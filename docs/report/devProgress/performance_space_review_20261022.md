# 性能、空间复查与单实例修复（2026-10-22）

## 范围和结论依据

本轮核对 Core 启动、PiP 采集/隐藏、录屏采集/编码/预览、GIF 调色板、录制文件缓存、OCR 交付和构建目录。性能条目来自当前代码路径分析，空间数字来自本机文件扫描；没有把代码分析当成 CPU/GPU 性能实测。性能优化暂列为后续候选，本轮实施单实例 bug 修复。

后续已开始落实前三项，当前实现、资源取舍和测量见 [第一批性能优化实施](performance_implementation_20261022.md)。下表保留审核时的证据与完整候选范围。

## 性能优化优先级

| 优先级 | 当前证据 | 建议与边界 | 验证方法 |
| --- | --- | --- | --- |
| P1 | `RegionStream::Read`、`DesktopRegion::Read` 对原始选区创建 staging 并读回，再在 CPU 上缩小到输出分辨率。 | 优先评估在私有采集设备上先做 GPU 缩小，再读回。4K 选区输出 1080p 时，原始 staging 像素量是输出的四倍；这是减少持续录屏资源占用最值得先测的路径。先改善缩放，不必立即引入跨进程 GPU 帧或修改 SDK。保留旋转、光标及颜色行为。 | 测 1080p/4K 源、30/60fps、核显/独显；比较 maxRead、CPU 时间、GPU 占用、峰值提交量和实际输出帧数；颜色/坐标回归必须保持。 |
| P1 | 监控最小化已暂停像素处理，自动隐藏持续一秒可回收捕获；最小化本身尚未走同一硬挂起路径。 | 将带源窗口销毁跟踪的延迟回收策略扩展到长时间最小化，可进一步释放 WGC 池与采集事件。短暂最小化保留迟滞，恢复时请求新帧；源窗口关闭、尺寸变化和恢复失败须有清晰处理。 | 持续最小化 30 秒比较 acquired/processed 计数、CPU 和 GPU 分配；恢复及源窗口关闭回归。 |
| P2 | `GifEncoder::Write` 对每个输出帧重做精确颜色探测或 WIC 调色板和像素索引；静态画面也重复。 | 评估相同画面复用上次调色板/索引，减少量化工作。保留帧时长，不把静止期间从动画删除。按当前上限增加一个 BGRA 对比缓存最多约 1.98 MiB；动态场景的比较扫描有额外成本，应先测再决定启用策略。 | 静态文本、少量滚动、连续动画三种负载比较 CPU；逐帧颜色和总时长回归。 |
| P2 | MP4 路径仍经过 BGRA 读回、CPU NV12 转换、共享内存及 MF 样本复制。 | GPU 编码不等于端到端无 CPU 复制。GPU 缩放改善后，再评估 GPU NV12/纹理编码或样本池。跨进程纹理需要明确所有权、同步和设备失效处理；MF 未释放的样本绝不能提前复用。 | 单独归因采集、转换、IPC、编码时间；以相同画质和时长比较，保留有界背压。 |
| P3 | `RecordSession::Status()` 多处在帧循环中复制包含字符串的完整 Snapshot。 | 可以按需拆出私有轻量状态读取，减少少量分配/锁竞争。收益预计小于像素读回，不优先为此增加新管理器。 | 先分析分配次数和 CPU 火焰图，确认开销可见后再做。 |
| P3 | Core 在启动时创建共享 D3D 设备；未启动截图也会有设备基础资源。 | 评估按首次图像操作创建设备，但当前宿主上下文包含设备指针，须先核对已加载插件及所有截图入口的初始化契约。不能简单把全局指针延后赋值。 | 空闲基线和首次截图延迟分别测；旧插件兼容性回归。 |

按像素格式计算，1080p60 的 BGRA 输出约 474.6 MiB/s，NV12 约 178.0 MiB/s；这是数据量，不是当前机器的实测带宽或 CPU 消耗。会话已有两个有界 BGRA 缓冲，1080p 合计约 15.82 MiB；不能为了省一个缓冲破坏“保留上一帧、忽略 S_FALSE scratch”行为。

OCR 已按任务启动 worker、限制推理线程，完成后退出；图片区段切除的历史保存坐标映射，未每次复制整张长图。这两处不应改回常驻模型或整图撤销快照。预览也已有最新请求合并、手势内解码器复用及结束回收，继续优化应先测寻帧本身。

## 空间快照和建议

扫描时，开发工作区 `build/` 约 **3638.25 MiB（3.55 GiB）**；这不是用户安装体积。

| 项目 | 扫描大小 | 判断 |
| --- | ---: | --- |
| `build/verify` | 1000.9 MiB | 当前完整验证目录，含编译中间件、测试结果、打包暂存。 |
| `build/ocr-deps` | 809.0 MiB | OCR 源码/运行库/模型构建依赖，多套构建共享；删除会增加离线重建成本。 |
| `build/verify-ocr`、`build/verify-ui` | 合计 1092.8 MiB | 历史验证构建，是最值得按需清理的开发空间；需先确认不再用于复现或运行。 |
| `build/verify/CMakeFiles/Nskry.dir/cmake_pch.cxx.pch` | 429.6 MiB | 单个较大的预编译头。缩减公共 WinRT 头或调整 PCH 使用范围值得评估；删除后会重建，禁用 PCH 则可能减慢编译。 |
| `build/verify/record-*` | 84.7 MiB / 158 个目录 | 测试和 benchmark 留存；其中 benchmark 约 78.0 MiB。宜增加显式可选清理或只在失败时保留，先保留最新验收证据。 |
| `build/verify/OCR*` | 68.3 MiB | 一些历史 OCR 包验证副本，可纳入开发产物清理；不要直接删除 `plugins/.../package` 当前 staging。 |
| `installer/bundled` | 20.75 MiB | 正式压缩插件包；其中 OCR 20.60 MiB、录屏约 0.11 MiB、长截图约 0.04 MiB。 |

用户安装体积的主要来源是 OCR 的 ONNX Runtime 和模型，当前 OpenCV 已只构建 core/imgproc。自定义精简 ORT 或模型量化有缩包机会，但维护成本和识别准确率风险更高，优先级低于清理开发副本；不能为了缩包删中文模型、许可文件或必要依赖。

录制剪贴板缓存需要保留文件供粘贴和剪贴板历史使用。当前 `PrepareRecordingCache` 启动前扫描并拒绝已超出 1 GiB/2048 项的缓存，**不是写入全过程的 1 GiB 硬配额**。适合后续增加用户主动的占用查看/打开目录/清理入口；删除前说明文件粘贴可能失效，不使用后台定时清扫。每次开始/修剪扫描目录也有 I/O 成本，但有项数边界，优先级低于持续像素处理。

本轮未删除任何开发目录、用户录制文件、缓存、测试或规划接口。

## 已实施：普通界面单实例

根因：`wWinMain` 在每次启动时直接进入 COM、GDI+、D3D、插件、快捷键和托盘初始化，没有单实例门槛。

新增 Core `SingleInstanceGuard`，在上述初始化之前保留一个命名内核对象句柄；名称按 Windows 用户 SID 区分，并使用 `Local` 登录会话范围。同用户同会话下，从不同目录打开的新版 Nskry 也只运行一个普通界面实例。重复启动静默退出；检查失败则报告 Windows 错误，避免继续启动第二套状态。

检查不持有 mutex ownership、不等待已有实例、没有轮询或新线程；正常/异常退出由系统释放进程句柄。已存在的旧版进程尚不具备此门槛，使用新版前应正常退出旧实例。多用户/多会话可以各自运行；跨提权状态尚未做实机验证。

现有 `--install-plugin` 一次性 CLI 仍在界面单实例门槛之前执行，保持安装器的调用方式；它不会创建普通 UI 托盘实例。本轮未新增 CLI 与 Registry 的跨进程事务机制。
