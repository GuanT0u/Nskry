# 翻译 0.3.0 两个插件包：公开图片自动化验收（2026-10-25）

## 结论

**流程可完成，不代表质量合格。本次两个包的图片端到端质量验收均未通过。**

- 两个公开图片，每个包各连续测试 3 次：12 次主测试全部完成，但全部存在原文或译文质量问题。
- 加上人工正确原文对照及额外诊断，共 24 次任务完成；观测到的离线 worker 均退出。
- 英文样本出现单词/数字拆分，中文户外招牌样本几乎未识别到目标文字。
- 即使绕过 OCR、输入人工正确英文原文，离线模型仍有错误、重复；将软换行合并后的一次对照中，原文 4 次事件被译成 8 次。
- 这些是所测样本、包、引擎与开发机上的实际结果，不代表所有中文图片均失败，也不是低配机器性能保证。

本轮仅增加开发测试工具、独立标准和报告，**没有修改生产 OCR/翻译算法，没有安装插件、停止用户程序或 push**。没有硬编码样本文字修复输出。

## 3. 自动化方法与评价边界

新增显式运行的 `NskryTranslationImageAudit`，调用真实插件截图入口及文字交接接口，读取自身结果窗口；每次借用位图在 execute 返回后即销毁，检查异步任务的位图所有权。顺序执行任务并维持消息分发，记录原文、译文、方向、状态、耗时、资源及 worker 退出情况。

主矩阵：2 包 × 2 图 × 3 次 = **12 次真实图片任务**；每个包每图另加一次人工正确文字对照，共 16 次。

额外诊断：带离线运行时包分别走离线、MyMemory，各图 1 次图片任务及 1 次文字对照，共 8 次；仅英文对照将人工文字的视觉换行换成空格。**没有改图片、没有改冻结标准，也没有将文字对照算成图片成功。**

自动指标：忽略空白的字符错误率 CER（大小写、标点仍敏感）、内容一致性、数字分组，以及忽略大小写的 Latin/digit WER。CER 会漏掉 `works → wo rks`、`12 → 1 2` 这种分词错误，所以同时检查词和数字。中文的 Latin/digit WER 只描述数字，不能当成中文通用词错误率。

翻译按人工预定语义逐项核对，不以非空、关键词命中或与参考译文完全一致来判定。工具中的 `workflow_success` 仅表示任务完成且产生输出，绝非质量通过。

### 英文实际识别的问题

原文应为 `a lot of 12 point`、`works`、`brown`，实际包含：

```text
This is a lOt Of 1 2 point text tO test the
ocr code and see if it WO rks on all types
...
lazy fox. The quick b rown dog jumped
```

非空白原文为 225 字符，字符编辑距离 5；空白忽略会让数字拆分看似无误，但 `12` 已变为两个数字组 `1`、`2`。离线译文出现 `IOt`、`tO`、`B型划划艇狗` 等错误，在线译文出现 `b绞狗` 等问题。均不能作为合格翻译输出。

### 中文实际识别的问题

四行 36 个非空白基准字符，得到的却是：

```text
一《。变叠、．新輳鼕：然@承 为0@，
```

编辑距离 36，CER 100%；目标 15/25/29/35 均未保留。离线输出 `One. Collapse, ... new: 0@,`，在线输出 `a. Variable overlap,. New congestion: however, @ is assumed to be 0 @,`。这是识别层失败，不能通过“翻译任务成功”掩盖。

## 5. 绕过 OCR 的对照：仍有翻译层问题

### 人工正确英文，保留视觉换行

- 离线 1547 ms，8 个分段；存在断句和 `懒懒懒懒狐狐狸` 等异常。
- MyMemory 7906 ms，按 8 行处理；即使输入完全正确，仍出现将 `jumped over` 译作 `跳了起来 / 在……身上` 等跨行语义损坏。

这说明单独修复 OCR 仍不够。代码按输入行处理，视觉换行会被当作独立翻译片段。

### 人工正确英文，仅合并软换行的额外对照

- MyMemory **1125 ms**：明显连贯，保留 4 次狗/狐狸事件；`12点文本` 对字号的表达仍不够准确。它是人工文字对照，不是原图路径通过。
- 离线 **2375 ms**：译文出现 **8 次** `狗跳过懒狐` 事件，原文只有 4 次。一次诊断的实际输出如下：

```text
这是很多12点的文本 测试ocr代码,看看它是否在所有类型的文件格式上都有效。快速棕色狗跳过懒狐。快速棕色狗跳过
懒狐。快速棕色狗跳过懒狐。快速棕色狗跳过懒狐。快速褐色狗跳过懒狐。快速棕色狗跳过懒狐。快速褐色狗跳过懒狐
。快速褐色狗跳过懒狐。
```

没有 OCR 错误、也没有这些视觉行边界后仍发生重复，必须进一步评估模型/解码忠实度，不能仅以段落合并宣称解决。此诊断只跑一次，不推断所有输入必然重复。

### 人工正确中文

两引擎均保留了 15/25/29/35 及物业对应关系，但离线将打浦路译为 `Pour Road`，在线为 `Tupo Road`；专名也有不稳定音译。因此只能说数字保留改善，不能说地址翻译已通过。

额外带离线运行时包的在线图片诊断耗时：英文 9766 ms、中文 1437 ms；同样未解决图片质量问题，且未启动离线 worker。

## 6. 与当前代码核对后的原因

1. **直接框选翻译与 OCR 插件并非同一识别链路。** `plugins/nskry-translate/src/nskry_translate.cpp` 的 `Recognize` 直接选择 Windows `zh-Hans` OCR 引擎，失败才选择用户语言；直接提交原始位图并将结果逐行拼接。没有使用 OCR 插件已有的模型、预处理与布局恢复。因此用户先 OCR 再翻译正常，与直接翻译识别差并不矛盾。没有在本轮证明 OCR 插件一定能识别这两张图片。
2. **视觉行被当成翻译段落。** 当前 MyMemory 与离线分段逻辑保留输入行；英文 8 个视觉行会形成多个独立处理单元。MyMemory 多次顺序请求及上下文损失可解释耗时和断句；请求数量根据代码/分段数推断，并非网络抓包计数。这不是对 OpenAI 兼容/LibreTranslate 请求切分行为的结论。
3. **离线模型自身仍需质量门禁。** 正确原文对照表明还存在模型/解码层错误与重复；不能全归因于 OCR，也不能靠字典或样本硬编码掩盖。
4. **专名、路名不能仅测数字或非空。** 数字正确不代表地址可用。

## 7. 资源与释放观察

测试顺序运行。测试专用观察线程约每 20 ms 采样内存、每 100 ms 查找本进程创建的翻译 worker，完成后立即结束；该观察器不是产品常驻功能，也未扣除其自身开销。

- 离线每任务观测到 1 个翻译 worker，所有观测句柄在任务结束后均为退出状态。
- 离线 worker 采样私有提交峰值约 **652 MiB**，物理工作集峰值约 **150 MiB**。二者定义不同，不可相加成内存用量。
- 主测试父进程采样峰值：离线私有提交约 15–23 MiB、工作集约 33–40 MiB；在线私有提交约 15–25 MiB、工作集约 32–45 MiB。包含图片解码、Windows OCR、测试窗口和观察器，不是纯翻译 DLL 的增量。
- 在线所有任务观测到的翻译 worker 数为 0，没有加载离线翻译模型进程。
- 所有任务仍进行 UI 消息分发；本轮未等同验证完整宿主里同时操作截图、监控的全部交互。
- 这些数据来自当前开发机，没有低配实测。CIM 硬件查询在本次受限环境失败，故不补猜 CPU/内存规格或宣称低配达标。
- 总耗时含 OCR/加载/网络/UI 分发；`source_observed_ms` 只是 UI 观察到原文的时间，不冒充精确引擎阶段计时。中文样本快速返回错误内容，不能当成有效性能成绩。

## 9. 建议的后续顺序（本轮未改生产逻辑）

1. 优先让直接翻译获得可靠原文：明确共用识别服务/可选 OCR 能力的边界，避免悄悄要求安装一个大功能前置，也避免承诺当前 Windows 原始 OCR 已足够。
2. 用坐标、行距、列间距恢复语义行/段落；不能简单把同一高度的远距文字或所有换行盲目合并。准确原文与几何布局应分开验收。
3. 离线模型/解码加入忠实度基准，覆盖重复句、数字、专名和长段落；先确认为何 4 次变 8 次，再决定解码或模型调整，不做样本词典式纠错。
4. 在线在不改变确认上传、配额、取消与资源释放边界的前提下，按语义段落减少顺序小请求；不将本次一次 1.1 秒的对照宣传为所有网络条件的保证。
5. 修复后继续沿用本次冻结标准，报告每个样本每次的真实输出；增加普通中文截图与低配实机覆盖，不能只测任务是否返回非空。
