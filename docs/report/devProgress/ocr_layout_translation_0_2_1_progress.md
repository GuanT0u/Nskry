# OCR 展示与直接翻译修复（2026-10-24）

交付版本：OCR 0.6.4、Translation 0.2.1。沿用上轮 Core 和现有语言包；API 2/可选联动协议不变。
未自动安装插件、未停止用户程序、未 push。翻译包仍为本地开发试用包，发行许可审计门禁不变。

## 1. 直接翻译偶发失败

用户错误 -2147483624 = 0x80000018 = E_ILLEGAL_DELEGATE_ASSIGNMENT。
不是“没有捕获到位图”的证据，也不是离线模型/语言包缺失。
核对当前 Windows SDK 的 windows.foundation.h：wait_for_completed 每次会调用 async.Completed(delegate)。
旧 Recognize 在循环中反复 wait_for(50 ms)，慢 OCR 超过首次等待后再次注册 Completed，因而失败。
OCR→翻译直接交接已有文字，不执行这段 Windows OCR 等待逻辑，解释了两条入口表现不同。

依据：[微软 Completed 文档](https://learn.microsoft.com/en-us/uwp/api/windows.foundation.iasyncoperation-1.completed)
明确说明完成处理器不能设置多次；同时以本机 SDK 的慢异步操作复现了完全相同的 HRESULT。

修复为任务 worker 内查询 Status + 可被取消事件唤醒的有限等待。不注册插件完成回调，
保留取消和 60 秒阶段超时，分别返回取消/超时错误；不会引入常驻线程或启动轮询。
UI 错误信息区分“截图文字识别”与“离线翻译”，不再把所有失败都引导到模型/语言包。

## 2. 右侧纯文本排版

新增纯展示模块 ocr_layout，不修改原始 pass、模型、arbitration、trace 或识别字词。
Windows OCR 与精确模式共用这层展示处理：

- 以纵向重叠、中心位置及相对字高的水平间距合并近邻片段，细小逗号/句号也可归入视觉行。
- 原始引擎行内部存在明显大间距时拆分，不能只因同一水平就连接两列/两个控件。
- 以行高、纵向间距、左对齐/列表续行缩进、标题宽度和新列表项判断段落续行。
- 标点本身不触发断行/断段；中英文连接使用基本标点/空格规则，不插入词典内容。
- 右侧 native EDIT 改为自动软换行，去掉横向自动滚动，否则合并后的段落仍会变成一长横行。
- 旋转后映射到竖列的文字保留引擎原文/顺序，不套用横排拆分规则。

这是保守的空间启发式，不是语义版面理解。多列/不明确的区域宁可分开；复杂表格、混合字号、
RTL/倾斜等仍需人工核对。现有翻译每段 256-token 上限保持，较长逻辑段落可能需要缩小选区/手动分段。

## 3. 左图高亮

- 默认改为缓存的逐视觉行/局部行段浅色填充（48/255 alpha），移除所有逐字符矩形描边。
- 段落连续性只影响纯文本；不会把多行高亮合并成段落高度的大块。
- 字符框仍用于命中、拖选、复制，不是可删除的死代码。选中覆盖使用系统选中色，关闭默认高亮仍可看到选择。
- 每次绘制只创建一套单像素覆盖 DC/位图，而非每字符创建并描边；连续选区按视觉行合并覆盖。
- 布局仅在结果生成时计算；候选行查询每片段最多检查 64 个近邻，避免极端几何导致无界二次搜索。
- 没有新模型、在线请求、待机任务或额外插件前置。未重新测量整机峰值/低配耗时，不宣称具体节省百分比。
