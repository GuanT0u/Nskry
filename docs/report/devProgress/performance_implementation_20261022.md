# 第一批性能优化实施（2026-10-22）

对应 [性能、空间复查](performance_space_review_20261022.md) 中优先级最高的 GPU 缩小、最小化采集回收和 GIF 缓存。其余缓存管理 UI、PCH 收敛、纹理编码、Core 设备延迟初始化仍为后续候选，未宣称已经完成。

## 1. 大选区 GPU 缩小后读回

- 新增私有 `GpuRegionReadback`，仅由采集会话的原有 MTA 线程创建和调用，复用其私有设备/context。没有给插件线程开放宿主共享 immediate context。
- 对需要缩小的 WGC 选区/窗口跟随，以及 Desktop Duplication 固定选区，在 GPU 上完成裁剪后的最近邻缩小和旋转映射，再读回目标大小的 BGRA。原有采样位置、alpha 和 BGRA 顺序保持不变；桌面光标仍在缩小后按原逻辑叠加。
- 资源按会话有界复用；没有新增帧队列或后台线程。未缩小的选区继续直接复制。GPU 初始化/处理不可用时，本会话保留原 CPU 缩小策略；设备移除仍明确失败，没有更换采集来源或绕过 Windows 指示边框。
- Shader 只在首次需要缩小时编译，不在 Core 启动或插件 init 中编译。测试中的三次初始化为 14.2–16.9ms。

三轮合成 3840×2160 → 1920×1080 基准，单轮 30 次读回，中位数如下。测试对照旧 staging + CPU 最近邻循环与新管线，不包含 WGC/桌面生产、H.264 编码或真实录屏调度。

| 指标 | 原路径 | 新路径 |
| --- | ---: | ---: |
| 每帧读回字节 | 33,177,600 | 8,294,400（减少75%） |
| 30次总 wall time | 461.588ms | 265.105ms（减少42.6%） |
| 本进程 CPU 时间 | 390.625ms | 218.750ms（减少44.0%） |
| 输出对照 | CPU 参考 | 三轮逐字节一致 |

每轮原/新 wall ms：653.454/265.105、340.553/234.171、461.588/336.557；CPU ms：500/203.125、265.625/218.75、390.625/250。变化幅度表明单轮速度有噪声，不把该比例写成所有机器的整段录屏加速比例。

资源取舍：4K → 1080p 时，原始 CPU staging 从约31.64MiB降至7.91MiB，但新管线另需源选区 GPU 副本约31.64MiB及 GPU 输出约7.91MiB。显式中间资源合计比原路径多约15.82MiB；驱动实际驻留/共享内存另计。此项主要改善 CPU 与读回带宽，不声称总内存同时下降。所有资源随采集暂停关闭/停止/失败而释放。

## 2. 监控最小化延迟释放捕获

- 最小化立即暂停像素处理，持续一秒后释放捕获对象和 WGC 帧池。恢复时重建采集并等待新帧，沿用已有 UI 状态和恢复失败提示。
- 将原来的自动隐藏延迟回收扩展到最小化；不强行把最小化窗口改为隐藏窗口。
- 即使用户关闭了“聚焦源窗口时自动隐藏”，仍保留针对源进程的窗口销毁事件，以便捕获已释放时仍能正确处理源窗口关闭。此时不订阅前台焦点变化，也不增加轮询。
- 无法注册源窗口销毁跟踪时，保持暂停像素处理，不硬释放捕获；避免失去源窗口关闭通知。
- 测试覆盖隐藏规则关闭时最小化、延迟释放、恢复、再次自动隐藏及源窗口关闭只报告一次。此项验证生命周期，没有独立测量整机最小化后的功耗/显存变化。

## 3. GIF 相同画面复用调色板和索引

- 编码器保留至多一张前帧；固定32点采样仅用于避免明显连续动画的缓存分配和复制。实际复用必须再做完整字节比较，哈希相同或采样未命中变化都不会错误复用。
- 发现相近画面后才按需分配 BGRA 缓存，最大960×540×4约1.98MiB，任务结束时随 worker 退出释放。帧数、帧延迟、局部调色板和输出格式不变。
- 回归包括连续相同画面、多次换场、回到旧场景及采样点以外的单像素改变，覆盖缓存与调色板关联错误。
- 以改动前保存的 worker（对应优化前提交 `14a8f6b` 的录屏实现）为基准，每种负载30帧、960×540，连续跑三轮。九组新旧 GIF 输出逐字节一致。最终三轮中位数如下：

| GIF负载 | 原/新子进程CPU ms | 原/新wall ms | 判断 |
| --- | ---: | ---: | --- |
| 静态 | 1046.88 / 765.625 | 1203 / 906 | CPU减少约26.9%，wall减少约24.7%。 |
| 30帧中6次变化 | 1062.5 / 859.375 | 1203 / 1016 | CPU减少约19.1%，wall减少约15.5%。 |
| 连续变化 | 1062.5 / 984.375 | 1172 / 1219 | CPU略降，wall约增加4%；波动较大，不宣称连续动画也更快。 |

静态/慢变化 worker 提交量约2.2MiB升至4.1–4.3MiB；连续变化约2.1–2.3MiB，没有分配前帧缓存。以上是合成GIF编码测量，不含真实屏幕采集。最终CSV保留在 `build/verify/gif-perf-10204-65185437`、`gif-perf-36616-65194187`、`gif-perf-20672-65202578`。

## 4. 测试与空间管理

- 合成 GPU 测试在 WARP 上核对裁剪偏移、四种旋转、整数及非整数缩放、动态源更换、alpha/颜色逐字节一致和输出边界。
- 真实采集回归使用测试自建窗口，新增320×180 → 160×90固定桌面和窗口跟随，两种均返回14,400个预期颜色像素；不采集用户应用内容。
- `build/verify` 完整 Release 构建通过，常用 `build/Nskry.exe` 与录屏插件包也已重建。最终按需缓存调整后的完整 CTest **32/32通过，86.92秒**；包括先前沙箱中被拒绝的网络/热键/采集测试，本轮允许它们使用所需 Windows API 后通过。
- GIF 对比基准仅在用户主动运行时执行；成功时删除本轮合成动图，仅保留 `metrics.csv`，失败时保留输出便于诊断。本轮清理了两个自己生成的预备基准目录内约106.49MiB合成 GIF，可通过基准重新生成；没有清理历史开发构建、用户录制文件或剪贴板缓存。

测试机器：i7-12650H、16GiB RAM、NVIDIA GeForce RTX4060 Laptop GPU（GPU基准实际选中该设备）。不是低配机；尚未验证四核/8GiB/核显机器的速度或 GPU 内存取舍，也未测真实视频场景的 GPU 利用率。

Core/API2/采集v1/v2布局及 reserved 不变；无额外插件前置、模型预热或常驻任务。已生成新录屏包但不自动安装，Core 更新与 GIF 编码 worker 更新是不同交付内容。

## 5. 第二批：录制调度与缓存入口

- 录制 worker 原先在每帧的状态判断、采样时间戳和等待时间计算中调用完整 `Status()`，连带复制 backend/message/recoveryPath 等字符串。改为私有 `ReadTiming()`，只读取状态和有效录制时长；仍在同一个互斥锁下读取，暂停、取消与时间戳语义不变。UI/测试的完整 Snapshot 接口保持兼容。没有新增线程、轮询或常驻缓存；尚未对该微优化单独测量 CPU 收益。
- 录屏插件设置新增 `Cache folder...`，复用设置栏原本空出的 Follow 位置。用户确认剪切板引用风险后才打开系统文件管理器；目录路径与输出生成共用一个私有函数。不自动枚举/删除，不更改剪切板，不触碰历史构建目录。缓存用量统计、选择性清理尚未实现，本轮先提供手动管理入口，避免误删仍被剪切板历史引用的文件。
- 新增设置入口的 UI 回归：只在设置模式显示、隐藏 Follow、打开设置不启动采集、关闭后正常卸载。测试不启动 Explorer、不操作用户缓存。保留已有暂停时长、重复停止、快速暂停继续、背压和资源回收回归，未为私有字段读取增加重复测试。
- 完整构建通过，常用 build 的 Nskry/录屏包也已重建；没有自动安装插件、停止用户程序或 push。
- 本轮最终完整测试 **31/32 通过（43.25 秒）**，`NskryRecordCaptureTests` 未通过。首次完整测试及单独复跑中，固定区域缩小采集返回 S_OK，但测试色像素为0；窗口跟随缩小采集14400像素正确，后续录制视频的时长及颜色解码通过。失败的缩小采集断言在 RecordSession 创建前执行，不经过本轮 ReadTiming 改动。尝试等待合成后仍未稳定通过，已撤回该测试改动，不能据此断定只是首帧时机或环境原因。须进一步定位实际桌面采集/显示环境，不能宣称本轮真实采集全部通过。日志见 build/verify/Testing/Temporary/LastTest.log（后续运行会覆盖）。
- 尚未实机验证 Explorer 打开/手动清理体验、低配机器收益；设备延迟初始化、编码零拷贝和历史构建清理仍未实施，不把保留接口或模型文件当作冗余删除。
