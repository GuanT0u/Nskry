## 已实施

### A1：直接销毁翻译 UI 时不再同步等待任务

原链路为 WM_DESTROY → Task 析构 → join / host recognition release。普通 WM_CLOSE 已异步取消，
但宿主/owner 直接 DestroyWindow 会走同步回收，提供者的取消响应时间可传导到主消息线程。

现在任务启动前先建立按需 message-only 完成窗口；沿用任务期间 50ms 检查，不新增线程或空闲轮询。
直接销毁 UI 只发取消，任务继续由此临时窗口领取结果，确认终态后才 join/release，并销毁定时器和窗口。
关闭后的结果不会写入新窗口，也不会自动开始翻译。清理期间新入口返回不可用/忙，不排队、不复用旧结果；完成后可正常重开。
正常关闭、取消、任务失败、无 UI 收尾和 shutdown 均有清理路径，DLL shutdown 仍先等待任务退出再卸载。

没有修改公开 image service v1 的 release=cancel+join 契约，也没有 detach 或强杀线程。
进程退出仍受合作提供者取消时间影响；不宣称可强制终止任意第三方 DLL，未以消息泵重入来伪装同步等待消失。

新增确定性测试：测试提供者需约 700ms 才返回取消终态；要求 DestroyWindow <250ms，
完成前不调用 release，等待期间独立 UI 心跳至少 5 次，完成后无任务窗口，可再次打开。
真实 OCR ↔ 翻译集成改为等待临时完成窗口回收，再申请下一任务，保留原来的独占、关闭与退出覆盖。

### B2：文本验证不再跨业务构造请求

新增小型无分配 UTF-16 验证 helper `sdk/nskry_text_validation.h`。
识别宿主直接检查自己的 text/length/limit，不再临时构造翻译请求。原 `NskryValidTranslation`
仍保留同名入口与版本/结构检查，委托相同规则；无 API 2 布局/保留位改动。
补 null、空白、长度上限、嵌入 NUL、合法/孤立代理项测试。未改变允许字符、文本长度或纠错行为。

### B1/C4 的有限收敛：共享算法按目标复用

布局与 OCR 子进程客户端分别成为内部静态目标 `nskry_ocr_layout` / `nskry_ocr_process`。
OCR、翻译、相关纯逻辑/进程测试通过链接使用，替代重复把私有 `.cpp` 列进多个 target。
在当前 native-model 全测试配置下，两份源码各从 4 处编译缩为 1 处，共减少 6 次重复编译。
这是构建工作量变化，没有测量完整冷构建加速百分比，不是用户安装体积或运行 CPU 的下降。

静态链接无新增 DLL/管理器/必装插件。没有迁移全部目录，源码和资产生产仍依托 OCR CMake；
从 OCR staging 复制自含模型的构建耦合尚在。未来独立公共资产目标需单独核对许可、hash、增量依赖及打包门禁。
没有为消除包内模型重复而把 OCR 变成翻译前置，也没有让 Core 加载模型。

### C3：手动审计工具不参与默认 all 构建

`NskryTranslationImageAudit` 改为 EXCLUDE_FROM_ALL，仍可显式构建，文档已补命令。
没有删除工具、测试断言、失败样例或降低识别标准；默认 CTest 列表不变。

## 第二批：录屏销毁回收与共享资产

本节为同日后续实施，上面的第一批验证数字和当时待办保留为历史记录。

### A2：录屏控制 UI 直接销毁

核对发现 WM_CLOSE 已对预览异步取消、对导出发取消，正常终态后 join；这些路径应保留。
但 WM_DESTROY 会清除原窗口定时器，未完成的 preview/export/session 没有后续领取者，
可能继续占用任务资源，甚至在没有控制 UI 时继续录制，完成后也不能清除 busy 状态。

新增插件私有 message-only 收尾窗口：随控制 UI 按需创建，平时没有收尾定时器；UI 直接销毁时
停止继续录制、取消预览/导出，由 50ms 临时定时器等任务确认终态后释放线程、采集、编码器和状态。
清理期间拒绝新的录制/设置任务，清理完可以重新打开；无任务时收尾窗口直接销毁。
没有新增管理器、额外插件前置或工作线程，没有修改 SDK、帧率/编码/预览背压算法。

异常销毁不是用户点击 Discard：已采集部分请求正常停止收尾，原录制、已完成的保存/修剪文件保留，
不会把用户未确认丢弃的内容删除；导出自己未完成的临时文件仍由 ExportTask 清理。
原来明确 Save/Discard/Cancel 的交互不变。后台故障留下的 recovery 文件仍可能不完整，不能承诺异常中断可恢复。
程序退出仍同步 cancel/join 以保证 DLL 卸载安全；若连收尾定时器也创建失败，退回安全同步清理，
不冒险 detach。此资源耗尽路径没有做故障注入，不宣称所有异常下都零阻塞。

新增真实流程回归：

- 在测试采集源 Close 内等待测试事件，强制资源释放延迟；销毁 UI <250ms，等待时 UI 心跳继续，资源结束后无残留任务，可重新打开。
- 预览拖动尚未松开时直接销毁 UI，确认 decoder/task 回收、原图像视频文件保留。
- 导出任务对象仍存在时直接销毁 UI，确认任务回收、原视频保留；不声称这里覆盖大文件慢磁盘的所有时序。
- 异常关闭保存的 MP4 用 Media Foundation 实际解码首帧；不是仅检查文件存在，也不是完整播放/时长实机验收。

### A2：更新任务核对结果

Settings 关闭调用 Cancel，任务由 Core 拥有，完成经消息窗口交给主线程；WinHTTP 的 stop callback
只设事件，网络及句柄回收在工作线程。现有同步 join 主要用于确认完成或进程退出，没有证据需要再造异步管理器。
补 350ms 延迟清理测试：Cancel 立即返回、busy 槽保留不排队、UI 心跳继续、取消后的旧 UI 回调不交付、完成窗口消失。
现有 stalled TLS 超时/取消、失败及退出测试继续保留。不将第三方网络/驱动任意卡死视为已解决。

### B1：运行资产不再递归复制另一个插件 staging

`cmake/ocr_runtime_assets.cmake` 按 native engine 的一份源/目标清单复制 14 个运行库、模型、许可文件。
OCR/翻译各自 staging，翻译不依赖 `nskry_ocr_assets` 或扫描 package/engine 内容；共享 worker
以 `$<TARGET_FILE:nskry_ocr_worker>` 单独复制，其构建输出路径仍在 OCR 目录。
不复制未知临时文件，保留所有原有许可、模型 hash 检查和包自含资产策略。
明确 BYPRODUCTS，使删除自己一个构建输出后也能重建。目录去重创建，文件 copy_if_different。
源码物理位置、依赖定义及 worker 生产仍在 OCR CMake；这不是独立引擎包，也不是运行时/安装插件前置。

实际两包 engine/ocr 的 **15 个文件（含 worker）SHA-256 全一致**。
独立临时 CMake 工程 `build/ocr-asset-stage-ca2d2d8f59/results.json`：
初次生成、无改动 no-work、源许可更新、缺失 byproduct 自动重建 **4 项通过**，包含带空格的路径。
这是手动构建回归，不增加普通用户或 CTest 的启动工作。
