# 后续性能与构建空间优化（2026-10-23）

## 1. 按需创建共享GPU设备

Core 不再在普通启动入口创建 D3DDevice。首次监控或实际插件初始化/执行才由 UI 线程创建，创建失败不留下半初始化全局对象，下次用户操作可重试。普通截图、固定截图、基础编辑和设置元数据列表不依赖此设备。

为保持旧API2插件兼容，PluginManager 使用宿主内部 graphics provider，在进入插件 init 前准备借用设备，并为 execute 的本地context副本准备同一设备；不更改SDK结构或reserved。不对声明身份/名称特殊判断。明确选择startup加载的插件依然可能在启动阶段触发设备创建，不能为省资源违背其旧初始化契约。已创建设备保留到插件shutdown及监控清理之后，不在插件仍可能借用时回收。

回归覆盖：metadata/快捷键发现不调用provider，设备准备异常不进入init并释放DLL，失败后重试，init和execute设备身份一致、execute准备失败不调用动作，shutdown清理provider，以及显式startup插件仍在init前准备设备。现有v1/v2/无输入扩展插件三组回归通过，录屏插件生命周期回归通过；未对真实主程序启动前后私有内存单独测量，不给出未经测量的MiB/CPU收益。

## 2. 公共预编译头收敛

公共pch仅保留WinRT base，采集projection、Foundation和COM interop按实际使用放进capture模块，避免JSON、配置、更新和普通编辑文件被迫解析WGC。不禁用PCH，不删除SDK/模型/规划接口，不对产品体积或运行内存作不实声明。

同一编译器/Release配置下，`build/verify/CMakeFiles/Nskry.dir/cmake_pch.cxx.pch`从450,494,464字节（429.6MiB）降为179,044,352字节（170.8MiB），减少258.9MiB/60.3%。常用build也重建为相同大小；两套当前构建合计减少约517.8MiB的PCH占用。历史build未删除，编译速度没有同条件前后基准，不宣称具体加速比例。

移除传递include后，完整构建通过；重建影响的全部源码及真实采集、监控UI等32项回归通过（54.72秒）。常用build/Nskry.exe也已更新。

## 3. 测试产物与设备成本测量

七组录制测试（features/session/process/control/color/encoder/capture）使用仅测试链接的Artifacts辅助类，成功后清理本次新建目录，失败/异常退出则保留。递归删除前校验目标为自己成功创建的绝对目录，拒绝根目录或后代reparse重定向；不会扫描/删除旧构建或用户缓存。`NSKRY_KEEP_TEST_ARTIFACTS=1`可保留成功产物。补充路径逃逸拒绝、失败保留、锁文件清理失败及仅删除自有子目录回归。没有减少测试断言。

增加已有GPU测试的显式 `--device-cost` 模式，默认CTest不运行此基准。三次独立进程测量D3DDevice构造：wall315.729/295.218/289.272ms，进程CPU328.125/312.5/250ms；设备存活时相对构造前私有提交量约46.4/45.4/46.2MiB。这是单独设备/驱动初始化成本，包含驱动加载，不是完整Nskry空闲内存或低配机测量；延后创建也会将这段开销移到首次需要GPU的操作。释放设备后驱动仍保留部分进程资源，因此不用“创建后马上销毁”冒充未初始化。

以上最终完整回归32/32通过（56.38秒）。只删除本轮测试自己生成且已成功验证的媒体，均可重新运行测试生成；未删除历史证据、用户文件或剪切板内容。

## 4. 静止帧复用已确认的编码输入

采集返回S_FALSE表示没有新图，先前仍每帧对同一BGRA执行NV12转换（GIF则重复复制BGRA）。增加IsolatedEncoder私有通道层的Repeat入口，重用子进程已确认归还的单输入槽，只提交新时间和时长。不是重用MF尚持有的sample，不新增缓冲、不更改协议或SDK；子进程仍每帧创建其拥有的输入sample并编码，因此静止期间的帧数和持续时间不变。

RecordSession仅在pending图像已经成功提交且未被S_OK新图替换时选择Repeat；新图、首次帧和替换后的最后收尾帧正常Write。S_FALSE的scratch像素仍忽略。首个输入之前、finalize之后、时间戳非法及通道关闭/失败时拒绝复用；取消仍走同一IPC取消/子进程退出逻辑。

回归比较带多次画面切换的MP4，正常Write与Repeat输出的逐帧解码NV12字节一致，时间戳/帧数/总时长一致；局部调色板变化后的GIF文件逐字节一致。补充未准备输入、错误时间戳、finalize后和取消中的Repeat测试；保留静止S_FALSE污染scratch、暂停恢复、源失败回收等测试。

比较时发现解码器把160×90可见图像输出到160×96对齐表面，未初始化的padding偶尔不同（首次差异在Y平面的第90行之后），已改为依实际MF尺寸/stride比较全部可见Y/UV像素，未增加颜色容差。RecordSession增加内部重复输入计数，测试确认静止时确实使用了优化路径，而不仅验证输出碰巧相同。

显式基准：`NskryRecordBenchmark --repeat-compare <验证目录>`，每组1920×1080/30fps/90帧静态图，硬件优先，三轮交替先后顺序。宿主仅帧循环CPU ms原/新为140.625/15.625、203.125/0、203.125/0；wall ms为219/171、344/172、282/218。0ms是Windows进程CPU累计计时分辨率下的结果，不是零开销。子进程总CPU原/新为609.375/703.125、703.125/593.75、687.5/953.125ms，驱动波动明显，不宣称编码器本身或整机CPU同步下降。六个MP4均解码90帧、3秒，成功验证后仅保留CSV：build/verify/repeat-perf-20584-39455890/metrics.csv。

该收益只适用于实际返回S_FALSE的静止/慢变场景；持续S_OK动画不会用像素扫描或哈希来猜测重复。低配核显及真实长时录制尚未测量，不外推本机基准。

有效像素比较修正后，features连续五次通过（19.38秒）；最后全量CTest **32/32通过，54.80秒**。两套构建及常用Nskry.exe/录屏包重建通过，未自动安装插件。生产代码已无临时像素/元数据输出。
