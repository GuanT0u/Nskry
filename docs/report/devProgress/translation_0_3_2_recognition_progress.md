# Translation 0.3.2：空间证据与可选 OCR 联动（2026-10-26）

状态：已实现、构建、回归及实际开发包测试；仍是本地开发版，不是全量识别/翻译质量放行。
本轮按 `translation_hypotheses_20261026.md` 的证据执行，不重写整个 OCR 或翻译引擎。
未安装用户插件、未关闭用户程序、未联网、未提交或 push。未触碰 `Paper Work/`。

## 1. 完成项

### 1.1 单次识别内的数字空间恢复

- 保留 CTC token 发射起止、局部分数，和用于显示的中点字框分开；没有把 blank 直接当空格。
- 仅对数字较多的行做轻量像素分析：Otsu 前景、完整连通字形，再核对有序且一对一的几何匹配。
- 同时要求真实留白、墨迹中心间距、CTC 时序间距的相对证据，以及至少两个一致的候选分隔；不按两位数、地址词典或具体号码拆分。
- 任一数字局部不确定、组件重复/遗漏、噪声太多或基线不足时保留原文。单个可疑空隙不猜；明确已有空格不删除。
- 新增空格也有字符范围/几何，保持复制、文字布局和选择的字符覆盖；内部 worker wire v1 未改。
- 普通图片仍只有一次 PP-OCRv4 模型识别。未引入固定增强六轮、大模型、FP32、增大 beam 或在线 OCR。

局部不确定性用于本轮空间判断，并保留在显式诊断输出；未把局部低分字符删除，也未凭低分猜成另一个字。
酒店行的 `曼→文` 仍保留实际输出。模型发射分数不是经过校准的正确概率，不能用整行高均分宣称每个字可靠。

### 1.2 可选使用已安装的 OCR 插件

入口：设置 → Plugins → 选中 Translation → 插件设置，或翻译窗口本身：
`Use installed OCR plugin for screenshot translation (optional)`。

- 默认关闭；改变/读取偏好不加载 DLL、模型，不联网。缺少 OCR 时给出安装/启用更新版的提示。
- 开启后仅通过宿主新建的可选版本化 **image recognition v1** 调用 OCR 0.6.5，无 UI 返回文本，再自动翻译。
- 使用 OCR 当前选定的 Accurate/Fast 路径，不重复打开 OCR 结果页；与 OCR UI 的队列、取消代次分离。
- 未安装、禁用、旧版、忙或失败时明确报错，不悄悄回退。用户可以取消勾选，继续使用翻译自带识别。
- OCR → Translate 的原有文字交接不受这个选项影响，已有文字不再 OCR。
- 旧 Core 没有连接新服务时仍能用翻译原有路径；即使偏好曾开启，也允许关闭它，不锁住用户。

当前两个默认 Accurate 后端本来就是同一个 PP-OCRv4，不能声称“只要安装 OCR 就必然更准”。
此选项让用户选择 OCR 的模式，并给以后 OCR 单独增强留下清晰的交付边界；目前剩余字形/专名问题按用户要求暂时保留，不硬修。

### 1.3 生命周期与资源边界

- API 2 基础结构和 reserved 未改，`requires_plugins` 拒绝策略未移除，原有插件无需更改。
- Registry、发现、加载、取消、结果领取均在 UI 线程；宿主复制借用图，后台只得到任务自有资源，不开放 D3D immediate context。
- 复用 PluginManager，任务实现按职责放在 `plugin_image_recognition.cpp`，不引入另一套管理器。
- 一个识别任务槽、零等待队列；输入 <=4MP、每边 <=4096，输出 <=16000 UTF-16 单元，版本/结果/字符合法性校验。
- 只在任务期间启动一个线程；复用翻译现有任务定时器，结果缓冲只分配一次，无空闲轮询。
- 关闭、取消、宿主销毁窗口、提供者卸载和整个程序退出都先取消/收尾；任何 DLL 释放前 join。
- Accurate 保持原有 <=4 线程、20 秒、1GiB 受限子进程，退出后才开始翻译；Fast 最多 3 个条件式 pass，增加整次请求截止与可取消等待。
- 修复回归中发现的 Fast 冷启动崩溃：MTA 结束前释放 DLL 内的 WinRT 工厂缓存，并保留异步输入位图直到操作结束。避免靠漏掉 COM 释放维持可用。
- OCR shutdown 也注销保留 DLL 窗口过程指针的三个窗口类；去掉妨碍同一 DLL shutdown/re-init 后重新注册的 once 标志，补充卸载后无残留类的回归。

接口/兼容契约：[image_recognition_extension_v1.md](../../plugins/image_recognition_extension_v1.md)。
原生第三方 DLL 仍不是沙箱；无法安全强杀不遵守取消契约的插件线程，不宣称宿主能强制它遵守 30 秒要求。

## 2. 验证与质量结果

### 2.1 开发反例与拒绝的方案

最初使用中点字框/列投影，虽能恢复招牌间距，却会误拆连续号码。扩大字体后仍发现退化，未作为最终包交付。
改为完整连通组件，随后增加一对一、有序匹配检查；重复组件会伪造很小的间距基线，必须拒绝。
失败 trace 仍保留，未通过修改人工标准或移除反例取得通过。

最终原 64 项分组正确数（raw → final）：0px 16→16、4px 6→6、12px 16→16、24px 12→12。
新增 256 项连续号码、小数、日期、IP、代码反例（4 字体 × 4 尺寸 × 2 颜色 × 8 文本），没有改变任何原始识别串。
这不把模型本来识别错的串计为正确；仍有未恢复的分组。扩展集已参与规则迭代，不再称为独立盲测集，也不推导普遍准确率。

显式诊断仍有 72 次六种预处理对照和 24 次原图 ROI 对照；没有把它们放进产品推理策略。
最终证据：`build/translation-spacing-20261026-verified/results.json`、`summary.json`。
重跑命令与非退化检查见 `tests/translation/HYPOTHESIS_TESTS.md`、`evaluate_spacing.py`。

## 5. 保留的问题及下一步边界

目前仍为有限但可用的识别/翻译，按用户要求先保持轻量路线。难字、细字、重复数字漏识别、单一可疑间距和专名/领域翻译仍可能失败。
需要更好效果时可以尝试 OCR 的不同模式；后续更高质量识别应在独立 OCR 插件内验证，不让 Core 或翻译变成常驻模型容器。
高 DPI/多屏、多窗口同时操作的手工体验、弱机、系统休眠/压力和第三方不合作 provider 仍需实机验证；不把已有自动化覆盖扩写为全部场景通过。
