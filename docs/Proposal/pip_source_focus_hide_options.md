# 聚焦监控源时暂时隐藏 PiP：三种检测方案与资源策略

> 2026-10-12：WinEvent、软暂停与稳定隐藏后重建会话的首版已实现。
> 详见 [实施报告](../report/devProgress/resource_first_features_20261011.md)；本文的恢复延迟目标仍待真实 WGC 验收。

日期：2026-10-11。状态：方案比较，未实现。总评见 [资源优先总案](resource_first_features_20261011.md)。

## 1. 当前实现核对

`src/main.cpp` 当前只有一个 `g_capture` 与一个 `g_pip`，另有多个固定图窗口。
`StartPiP` 持有捕获目标 HWND，但 PipWindow 本身没有目标句柄/自动隐藏状态。
`CaptureSession::OnFrameArrived` 总是取帧并 ProcessFrame；PipWindow::RenderFrame 总是缓存并 Present。
不可见/最小化没有明确的处理暂停门禁，因此只加 SW_HIDE 不能保证节省采集成本。
`CaptureSession::Stop` 是终止式清理，`m_stopped` 后 Start 不会恢复，不能把 Stop/Start 当暂停 API。

以下“挂起”解释为已创建的悬浮实时监控 PiP，不是冻结帧、停止任务或固定截图。
只对目标监控窗口增加自动隐藏；固定图不因为用户切回某个应用而自动隐藏。

## 2. 行为契约

- Settings 提供“聚焦监控源时暂时隐藏监控窗口”，建议默认关闭以保持现行为；启用后立即评估当前前台。
- 右键提供带勾选的“自动隐藏：跟随全局/本窗口开启/本窗口关闭”；窗口级覆盖本次生命周期，
  修改全局默认仍在 Settings；用户明确区分两者，不能右键静默改全局。
- 前台为所监控源的根窗口时隐藏，切到其它应用时自动恢复，恢复使用 SW_SHOWNOACTIVATE，不抢焦点。
- 不仅按 PID 匹配：同一浏览器另一个窗口不必隐藏。源拥有的模态对话框可按 owner 链归属，首版规则明确可测。
- 自动隐藏、用户最小化、编辑/菜单临时保护、源已关闭是不同状态；不能因焦点变化恢复用户主动最小化的 PiP。
- PiP 编辑、右键菜单、其工具栏在操作中不突然自动隐藏；关闭操作结束后重新评估。
- 开启时若源已前台可立即隐藏；用户可在 Settings/托盘管理入口关闭该功能，隐藏状态必须仍可恢复控制。
- 源关闭/目标失效直接走现有关闭流程，不因 HWND 数值被复用误认新窗口；持有有效捕获对象并跟踪销毁。

## 3. 方案 A：系统前台事件通知（推荐）

在 Core UI 消息线程注册一份 `EVENT_SYSTEM_FOREGROUND` 的 `SetWinEventHook`，
使用 `WINEVENT_OUTOFCONTEXT`，不向外部应用注入 DLL；仅有监控且开启功能时注册，最后关闭时撤销。
回调只投递/合并重新评估消息，UI 线程查询最新前台并执行纯状态转换，避免重入、过时事件和裸对象指针。

不使用 SKIPOWNPROCESS：Nskry 自己成为前台时也需要重新评估/恢复，其菜单保护由状态判断，不能漏掉该切换。
系统空闲没有该功能的轮询定时器；事件少时只做少量句柄比对。注册失败应明确说明并提供受限回退。

依据：[Microsoft SetWinEventHook](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook)。
OUTOFCONTEXT 在注册线程交付，线程需有消息循环；文档也提示回调可重入。因此保持轻回调与 UI 状态机。

## 4. 方案 B：低频前台轮询

仅在功能开启且存在 PiP 时用定时器查询 GetForegroundWindow；建议 200–300 ms，窗口结束即 KillTimer。
无需全局事件订阅，代码最简单，对事件通知不可用可作为回退。

代价：桌面完全不变也每秒唤醒 3–5 次；响应迟到最多一个周期，容易在源前台出现短暂遮挡。
10–16 ms 快速轮询更耗电，禁止把定时器间隔缩短作为常规修复。
不能在每次查询时枚举全部窗口/进程或读取截图。

## 5. 方案 C：Shell 激活消息

Core 消息窗口通过 RegisterShellHookWindow 订阅 Shell 消息，处理窗口激活通知后评估源。
属于窗口消息模型，与 A 的无障碍 WinEvent 和 B 的主动查询不同，也不需定时轮询。

代价：Shell 生命周期/替代 Shell/通知差异需要处理；官方标注该函数不适合一般用途且未来版本可能改变。
若只想看前台，使用这一更宽的 Shell 通知面没有明显收益。
不改为全局 WH_CBT/进程内 hook，后者引入注入、位数/权限和维护成本。

依据：[Microsoft RegisterShellHookWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registershellhookwindow)。

## 6. 资源比较

| 方案 | 无焦点变化时的新增唤醒 | 常驻资源 | 响应/兼容成本 | 判断 |
| --- | --- | --- | --- | --- |
| A WinEvent | 不主动轮询；只处理相关事件 | 一份 hook 和小状态 | 官方前台事件、需重入保护 | 资源/兼容平衡最佳 |
| B 轮询 | 每秒 3–5 次 | 一份 timer 和小状态 | 简单但有延迟 | 仅失败回退 |
| C Shell 消息 | 不主动轮询 | 一份 Shell 注册 | 更宽通知面、支持稳定性较差 | 不作主方案 |

A/C 空闲成本均可能很低，不能未经测量说 A 在每台机器上 CPU 绝对更少；
**推荐 A 是最窄的适用事件面和最低必要复杂度**。相比固定轮询，空闲无需周期唤醒更符合目标。

## 7. “隐藏”与“省资源”分别设计

以下资源策略可组合上述任何检测方案，不把窗口不可见误当 WGC 已停止。

### R1：只隐藏 UI（不足）

SW_HIDE、隐藏工具栏/阴影；采集、GPU crop、缓存复制、Present 都不变。
改动最小，但节省有限，不推荐作为完整交付。

### R2：软暂停应用处理（短暂切换首选）

隐藏后设原子处理门禁，在 FrameArrived **取出并关闭帧**，不进入 GPU crop/消费者/Present。
不能只提前 return 而不释放池中帧；退出/取消仍保持现有回调 drain 和对象生命周期。
保留最后可见帧用于恢复占位，不再生成新 CPU 副本；恢复下一帧核对尺寸和设备状态。
该策略降低应用侧处理，但 WGC 会话/平台采集仍存活，不承诺系统 GPU 采集归零。

### R3：隐藏稳定后终止并按需重建采集（长时间隐藏最低稳态资源）

立即 R2；若仍因源聚焦隐藏，建议一次性 1000 ms 延迟后关闭采集对象，保留目标/crop/窗口与最后帧。
不在隐藏期间轮询；恢复时重建 CaptureSession，恢复第一帧到来前显示最后帧且明确其尚未刷新。
Stop 是终止式，因此必须重建，不能调用旧对象 Start。重建失败需提示并可重试，不能静默显示“实时”的旧帧。

重建会有短资源峰值和恢复延迟；快速反复 Alt-Tab 下每次都 Stop 最浪费。
延迟为待测策略值，不是保证；第一版设计支持调整这个内部阈值，不给 UI 堆更多选项。
必须保留源销毁通知能力：关闭 capture 后若不再订阅 item.Closed，应保留对应目标的销毁事件追踪，
或保留轻量 capture item 及 Closed 订阅，不能失去来源身份或把资源终止等同忘记源状态。

### 综合推荐

**A + R2 即时门禁 + R3 稳定隐藏回收**：兼顾常用快速切换与长时间在源上工作的稳态节省。
R3 的隐藏状态通常比 R2 更省 GPU/RAM，但对很短隐藏的总成本可能更高；需测恢复 p95 决定阈值。
若重建在低配机无法达标，可先交付 A+R2 并明确其限制，不虚报“隐藏后完全零采集”。
严禁在 FrameArrived 内 Stop 等待自己的 drain；状态转换不能持 renderMutex/callbackMutex 再等待 Stop。
只在 Core 维护 controller，main 负责连接；不把完整状态机塞进 main.cpp，不给插件全局焦点访问权限。

## 8. 状态与验收

建议可见性由多个原因组成：UserMinimized、SourceFocused、Closed；菜单/编辑保护是单独的临时抑制策略。
仅当 SourceFocused 消失且其它隐藏原因均不存在才自动显示。全局设置失败需回滚并提示保存失败。

纯逻辑测试：源→其它应用、其它应用→源、同进程不同窗口、owned dialog、前台为空、覆盖切换、关闭、用户最小化。
生命周期：快速 Alt-Tab 50 次，R3 延迟撤销、恢复时关闭、设备丢失、源 HWND 销毁/复用，菜单期间不失去控制。
资源：记录每帧取出/关闭、GPU crop、cache copy、Present、重建次数；R2 下后三类为零（允许状态切换时一帧已在途）。
R3 后无采集帧回调、无恢复轮询；切换不抢焦点，隐藏工具栏/所有阴影一起消失。
