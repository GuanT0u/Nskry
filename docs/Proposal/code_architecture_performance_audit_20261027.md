## 1. 审核目标和判断规则

以 `docs/architecture/core_plugin_contract.md`、`docs/plugins/development_standard.md`、公开 SDK 和实际调用链共同判断，不能仅依据文件名、行数或搜索命中删除内容。

- Core：通用框选、编辑、固定/监控窗口、生命周期、元数据和版本化调度；不承载识别/翻译模型、录制编码或业务纠错。
- 插件：各自业务与结果 UI；依赖公开宿主契约或自含私有库，不读取其他已安装插件的内部目录。
- 共享源码可以复用，但共享构建目标应有清楚归属；不为复用几段代码新增常驻服务、管理器或必装插件。
- 高内聚按职责和变化原因衡量，不是把所有同名代码放进一个文件；低耦合也不是禁止必要的协议依赖。
- 性能以空闲、任务峰值、收尾三段分别评估；不以常驻模型换冷启动成绩，不以删除行为/降低质量冒充无损优化。

每条正式发现需记录：路径/函数、调用链、可复现证据、用户影响、优先级、最小改动、兼容边界和回归方法。待测风险不得标作已发生故障。

## 2. 初查结果与优先级

P1 表示先验证生命周期/响应性；P2 表示结构及有证据的资源候选；P3 表示维护或构建成本。当前未确认 P0 缺陷。

| 编号 | 优先级 / 证据状态 | 位置与初查事实 | 审核及处理方向 |
| --- | --- | --- | --- |
| A1 | P1，存在同步等待路径，阻塞时长待测 | `src/core/plugin_image_recognition.cpp` 的 ImageJob 析构 cancel 后 join；Translation Task 析构调用 release。普通 WM_CLOSE 已先取消并等任务结束，但直接 WM_DESTROY/退出走同步回收。SDK 的 30 秒是提供者合作约束，不是宿主强制截止。 | 用延迟取消的测试提供者测 UI 心跳及退出上限。区分普通关闭、直接销毁、退出、提供者卸载；必要时让存活宿主持有待回收任务至完成，最后才卸载 DLL。不能简单 detach、卸载仍运行的 DLL 或强杀线程；是否需要新扩展必须先核对 v1 release 契约。 |

## 3. 哪些可删、哪些不能删

目前没有足够证据认定某个生产函数可以直接删除。正式清理采用以下分类，不把“非核心功能”等同于“无用代码”：

| 分类 | 处理原则 |
| --- | --- |
| 确定死代码 | 必须证明无直接/间接调用、无导出/动态符号/消息入口/构建变体用途，也非未来契约。满足后删除，补编译矩阵。 |
| 重复实现/重复真值来源 | 比较行为、错误路径和所有权后统一，例如公共文本检查或 CMake 源文件列表；不机械合并相似 UI。 |
| 可选体验 | 阴影、圆角、快捷键跳转、Cut 样式等是已承诺功能，保留；只优化隐藏或关闭时的资源。 |
| 兼容与规划 | 保留 API 2 布局/reserved、版本检查、未知配置、staging/rollback、standalone 预留、旧输入导出兼容。只清理不符合规范的具体实现，不删能力边界。 |
| 诊断和故障注入 | 属于开发验证，不进入正常用户路径；检查编译/运行隔离。不能把测试 worker 中的故意挂起直接当作生产死循环。 |
| 历史 build 和媒体 | 与生产代码分开管理，先标明可复现性、进程占用和用户引用；本轮不删除。 |

测试也按风险覆盖审查：纯状态机/边界、宿主 runtime、真实插件流程各有目的；名字或输入相似不等于重复。只有证明断言、故障路径和环境覆盖完全被替代，才合并重复测试。外部网络/模型质量矩阵保留显式运行，不加入每次默认回归。不得通过删失败样例、放宽标准来变绿。

## 4. 实施顺序与阶段门禁

### 阶段一：基线、依赖与生命周期（优先）

1. 固定当前提交/构建选项、依赖版本、机器配置；跑现有完整测试，模型 OFF 单独记录，不沿用旧 46/46 成绩。
2. 输出 Core→SDK→插件→worker 的源码/构建/运行三张依赖表，记录每条跨层调用与资源归属。
3. 优先完成 A1/A2 的取消、关闭、失败、退出回归。用测试自有窗口的消息往返测量响应性，不靠只检查最终退出判通过。
4. 产出可复现发现；真实 UI 阻塞先修复，再推进结构清理。

### 阶段二：有限结构纠偏与冗余整理

按 B1/B2/C3/C4 逐项评估小提交；只对当次涉及模块做 B3 拆分。每次保持可构建，不改变 API 2 布局、当前设置、插件安装独立性和现有输出。
加入最小 Core + 单插件、缺失/禁用可选提供者、旧扩展、model ON/OFF 的覆盖。必要时同步规范中真实归属，不让文档抢先宣称新服务已经实现。

### 阶段三：性能归因后优化

基线包含：仅托盘、打开/关闭设置、监控可见/最小化/隐藏、OCR 与翻译启动至退出、录屏静止与动态 30/60fps、预览拖动。
记录 CPU 累计、私有提交、工作集、线程/句柄/GDI、GPU（可获得时）、任务 wall time、收尾耗时；完成后立即与 5/30 秒检查无遗留 worker/定时器，不要求驱动/系统缓存必然回到逐字节相同值。

同一构建配置、输入、冷/暖条件下交替 A/B，至少 5 次，报告中位数和范围；要报告 P95 时使用足够样本（例如至少 30 次），不要从三次测试推断 P95。
质量使用现有冻结文本/像素/时长标准；任何加速不得掩盖识别退化、丢帧、暂停空白或错误颜色。

参考设备分组是待测矩阵而非保证：低资源组 4 核/8GiB/核显/SSD；常规组 6–8 核/16GiB；高资源组 8+ 核/32GiB。仍需记录具体 CPU 型号代际、功耗模式、内存和 GPU 驱动，不能仅凭核心数归类。现有 i7-12650H 数据不代表低资源组实测。

### 阶段四：完整回归和报告

全量构建/测试、关键生命周期重复回归、运行中资源回收及实际 UI 验收。输出已修/未修、收益与代价、兼容边界、尚缺设备验证。没有效果的性能改动不保留复杂性；测试不足则标明不足。

默认不安装插件、不停止用户程序、不清理历史证据、不 push。构建被占用时使用独立验证目录；是否提交按实施时用户授权执行。

## 5. 本轮不重复实施的已完成项

据 `performance_followup_20261023.md` 和对应实现记录：GPU 缩小后读回、监控最小化硬挂起、GIF 相同画面量化复用、轻量帧状态读取、共享 D3D 按需创建、静止编码输入复用、PCH 收敛、成功测试产物按归属清理均已有实现。此次深审应验证其边界和回归，不将其再次列作新优化成果。

总体初判：尚无证据表明项目整体偏离 Core/独立插件路线；值得收敛的是共享源码的构建归属、少量跨业务类型复用、逐渐增长的入口文件，以及任务销毁时 UI 响应性的边界。优先解决这些实际问题，不为“解耦”提前建设 API 3 通用服务系统。
