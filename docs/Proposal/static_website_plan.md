# Nskry 静态官网与插件目录规划

日期：2026-10-28。状态：本地静态首版已实施，尚未配置域名或部署。

实施进展：2026-10-28 已完成本地静态工程、内容与发布数据校验、catalog 本地生成及页面验证。
尚未配置域名、部署或接入客户端官方更新。详见 [实施报告](../report/devProgress/static_website_20261028.md)。
目标：发布安装包、浏览和下载插件、阅读教程；先确定内容与发布流程，视觉样式待选模板后调整。

## 1. 推荐方案

使用 Astro 静态输出 + Markdown 教程 + 构建时读取的结构化发布数据。
首版网站放在主仓库独立的 `website/` 中，与 CMake、桌面运行时和插件编译隔离。
网站不参与桌面默认构建，也不使 Nskry 运行依赖 Node.js。

页面输出纯静态 HTML/CSS，只有筛选、搜索、复制校验值等必要功能使用少量浏览器 JavaScript。
不设账号、数据库、后台管理、支付、评分、评论、下载计数或自动上传插件系统。
内容通过 Git PR 审核发布；无需给开发者提供网站写入账号。

默认候选部署为 GitHub Pages；安装包、插件包和必要源码归档使用版本化 GitHub Releases 资产，
不把大文件提交进网站源码或放入页面构建产物。之后可换静态托管和下载镜像，内容结构不变。
这一选择重在维护简单；不预先承诺任何地区的访问速度，正式上线前测试主要用户地区的页面和下载可达性。
域名和具体托管账号待部署阶段确定；目前不填写虚构官网地址。

Astro 可在构建时生成静态页面，GitHub Pages 可托管静态 HTML/CSS/JS；官方资料见文末。
若后续选中的模板采用其他静态工具，可替换展示层，保留下面的数据契约与 URL 结构。

## 2. 页面与信息结构

| 路径（相对站点根） | 内容 |
| --- | --- |
| `/` | 简要介绍、实际功能截图、下载、插件和教程入口 |
| `/download/` | 最新稳定版、系统要求、安装说明、已知限制、源码和 SHA-256；无稳定版时明确显示开发/预发布版 |
| `/releases/`、`/releases/<version>/` | 版本历史、变化、兼容性、固定版本资产和对应源码 |
| `/plugins/` | 官方/第三方分类、功能标签、简单搜索筛选、兼容范围、发布状态 |
| `/plugins/<id>/` | 插件详情、实际包变体、安装/配置、更新来源、作者和支持入口 |
| `/guide/` | 安装与首次截图、钉住/监控、图片编辑、插件安装更新、OCR、翻译、录屏、常见问题 |
| `/developers/` | 贡献指南、SDK、插件规范、插件目录收录流程的摘要和源码文档链接 |
| `/about/` | 项目来源、免费获取渠道、许可/第三方声明、隐私、官方身份与反馈方式 |
| `/notices/` | 影响用户的已知问题、版本撤回或安全公告 |
| `/catalog/plugins-v1.json` | 给客户端读取的官方插件更新目录，不是网页详情数据 |

首版中文优先，保留翻译内容组织空间，不预先复制一套未翻译页面。
核心下载和教程不依赖 JavaScript；插件目录较小时仅做本地筛选。
全文教程搜索等内容增长后再引入静态索引，不为几篇教程引入远程搜索服务。

## 3. 下载与插件市场

“市场”首版是经过维护者审核的静态目录，不含交易或自动安装。
用户下载 `.nskryplugin` 后，在 Nskry 设置中安装；不虚构尚不存在的一键安装协议。

插件详情至少包含：

- ID、名称、简介、功能截图、作者/团队、源码、许可证、维护/支持地址。
- 官方或独立第三方分类、由谁维护；收录不等于官方认证，不用作者自填字段授予官方身份。
- 发布状态（开发版/预发布/稳定/已撤回）、版本、日期、系统/架构/Core/API 兼容范围。
- 每个下载包的文件名、HTTPS URL、字节大小、SHA-256、包含的运行时/模型、额外配置要求。
- 是否联网、哪些数据会发送到哪里、所需凭证，以及功能限制。
- 安装、启用、重启应用更新、禁用和卸载的说明；第三方插件风险提示和发布者更新地址。

在线/离线是**包变体**，不能只用同一个含糊的“下载”按钮：

- 在线版：注明是否包含截图识别引擎、需要自行配置的服务和密钥，不承诺免费额度。
- 离线版：注明是否包含翻译引擎、语言模型是否另行下载、模型放置/配置方法。
- 不完整开发包不得作为推荐安装包；离线运行时缺失不能靠填模型路径解决。

网页可展示多个变体，但当前更新协议按插件 ID 返回单一版本/包地址，没有变体协商。
同一 ID 的在线/离线包不能重复塞入官方 catalog，也不能随意选一个使用户更新后丢失离线能力。
存在此问题的插件暂不接入自动更新目录；先确定统一完整发行包，或另行设计版本化变体更新协议。
网站规划不擅自改插件 ID 或升级 SDK。

第三方收录流程：作者提交元数据/详情 PR → 核对包来源、许可、兼容信息和链接 → 维护者审核 → 静态发布。
审核不运行投稿附带的任意脚本；第三方默认链接发布者的固定版本资产，不静默替其托管或改写包。
撤回条目保留说明与版本记录，移除推荐下载入口；不远程删除用户已安装插件。

## 4. 数据与客户端接口

建议组织（实施时创建）：

```text
website/
  src/content/guides/          # Markdown 教程
  src/content/releases/        # Markdown 发布说明
  src/content/plugins/         # Markdown 插件详情
  src/data/releases/           # 安装包版本、资产与来源记录
  src/data/plugins/            # 插件元数据及包变体
  src/layouts/                 # 将来替换模板的主要位置
  src/components/
  src/pages/
  scripts/                    # 校验、生成 catalog
  public/                     # 图标、小型静态资源
```

结构化数据由构建期 schema 校验，页面和 catalog 从同一份发布记录生成，避免分别手填版本/校验值。
网页元数据可有截图、标签、变体等字段；客户端 JSON 仅输出当前解析器支持的更新字段。

已核对 `src/core/plugin_update_policy.cpp`、`plugin_update_manager.cpp`、`settings_manager.cpp`：

- 当前官方 catalog 使用 `schema: 1` 和 `plugins` 数组；条目有 `id`、`latest_version`、
  `package_url`、`sha256`、可选 `min_nskry`、`max_nskry` 和 `release_notes`。
- URL 必须 HTTPS，版本须为合法 SemVer；每个 ID 只有一个条目，构建时对全部条目校验，
  不依赖客户端仅校验已安装匹配条目的行为。
- `updates.official_plugins_page_url` 指向插件网页，`updates.official_plugin_catalog_url` 指向静态 JSON。
- 官方来源记录查官方目录，第三方记录查其自身 update URL；从官网手动下载再本地安装，
  **不会因此自动变成官方来源记录**。上线联调必须覆盖这条路径，不能只填两个 URL 就声称集成完成。
- 仅用户检查更新时联网。网站上线不改成桌面启动联网，不增加后台轮询。
- 此接口负责插件更新；不能拿它冒充主程序自动更新接口。主程序首版从下载页手动更新。

静态 JSON 不需要后端。首版不要在访客浏览器里逐个请求 GitHub API 或第三方更新地址。
更新元数据应较快生效、避免长期陈旧缓存；固定版本资产及带 hash 的 CSS/图片可长缓存。
具体响应头能力按选定托管平台实测，无法控制时不宣称已实现自定义缓存策略。

## 5. 官方目录与发布边界

沿用现有 [发行治理规划](../governance/distribution_and_brand_protection.md) 和
[第三方插件政策](../plugins/third_party_policy.md)，本方案不改变许可证。

下载页/教程可以先上线。正式“已验证官方更新目录”另有前置：发布者认证记录、签名验证、
客户端信任根、密钥轮换及撤销设计。当前客户端的来源字段和 SHA-256 都不等于密码学认证。
未完成前，不展示“签名已验证”徽标、不把空目录解释为所有插件已是最新版。
签名密钥不能进入网站源码、PR 预览或浏览器；未来签名也可离线生成，不必增加常驻网站服务器。

官网仅推荐通过实际发行检查的安装包和插件。当前翻译开发包及尚未完成依赖/模型发行审核的产物，
不能因为页面做好就升级为正式稳定版。每个发布版本应关联相应源码、构建资料和许可声明。
网站允许说明官方免费渠道，但不把合规 fork 销售或安装服务说成盗版。

## 6. 发布流程与校验

1. 独立完成软件构建、测试和包/许可检查，形成明确版本的资产与源码记录。
2. 将文件发布到固定版本地址，计算实际文件 SHA-256 和大小；同版本文件不偷偷覆盖。
3. 更新网站数据及发布说明，PR 检查 schema、重复 ID、兼容范围、链接、必填项和发布状态。
4. 检查下载可用性与包内容；重定向后的真实地址须同时经浏览器和 Nskry 下载器验证。
5. 先部署预览，审核后发布页面；适用时最后更新 catalog，确保不会指向尚未上传的文件。
6. 发布后抽查下载、校验值和客户端手动检查更新，保留上一份网站构建产物以便回滚。

页面回滚与软件降级不同：当前客户端只推荐更高版本，不能靠下调 catalog 版本自动给用户降级。
坏版本先撤回推荐并公告，修复后发布更高版本；个别手动恢复流程另行说明。

未来 CI 分开处理：不受信任 PR 只构建/校验，不持有发布密钥或软件签名密钥；
正式部署仅使用已审核分支/版本。不要用有写权限的任务直接执行投稿者提供的构建脚本。

## 7. 分阶段实施与验收

**A：内容与本地骨架**

创建隔离的静态站工程、内容 schema 和简洁基础样式；完成首页、下载、插件列表/详情、教程与 404。
先导入经核实的版本资料，没有正式资产就明确显示未发布，不生成假下载链接。
验收：可本地构建；无后端；禁用 JS 仍可下载和阅读；移动端/键盘导航可用；内容链接正确。

**B：发布与目录数据**

补发行历史、包变体、第三方收录规则、数据校验和可重复部署流程；确认域名/托管后部署。
验收：页面与下载 hash 一致；实际安装包可获取；第三方身份明确；无敏感数据/未授权素材。
catalog 可先在本地生成并跑解析测试，正式接入受第 5 节约束。

**C：客户端联调与正式发布**

解决官方来源安装路径、认证/签名及变体策略后，配置真实官网/catalog URL。
覆盖新装、第三方本地安装、官方更新、无兼容版本、网络失败、撤回版本及旧客户端。
验收：网页和客户端描述一致，不把未检查当最新，不改变按需联网原则。

**D：替换视觉模板**

用户选定模板后只调整布局/组件/样式，核对模板许可、依赖和资源体积。
保留下载地址、内容 schema 和已公开页面路径；确需改 URL 时提供适当重定向。

首版不实现账号、付款、自动插件上传、评论、热门榜、下载统计、实时评分或远程安装。
待确认项只包括域名、托管账号和视觉模板，不阻塞 A 阶段本地开发。
