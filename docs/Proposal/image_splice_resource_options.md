# 通用图片区段删除与拼合：三种资源方案

> 2026-10-12：区段映射路线已进入 Core，普通图无需 Scroll 前置。
> 详见 [实施报告](../report/devProgress/resource_first_features_20261011.md)；本文保留实施前方案比较及性能目标。

日期：2026-10-11。状态：方案比较，未实现。总评见 [资源优先总案](resource_first_features_20261011.md)。

## 1. 实际代码与功能边界

当前 `src/ui/long_image_crop_window.*` 是 Core 共享编辑器，只支持矩形裁剪，
`CreateRegionBitmap` 用 BitBlt 导出一个连续区域；不是 Scroll 插件的 UI。
`Paint` 当前每次创建客户区大小的后备位图，扩展时应避免再按整张长图分配预览缓冲。
固定图/PiP 的 Edit 当前进入各自标注流程，并不自动进入共享结构编辑器；新功能需要增加明确的“裁剪/区段编辑”入口。
OCR 使用宿主编辑回调，仍然不依赖 Scroll。

功能归属确定为 **Core 的通用结构编辑**，适用于普通图、长图、固定图、监控静态帧及 OCR 原图。
不实现任意矩形挖空补图、不拉伸文字、不改变实时监控源或采集裁剪区域，不增加插件前置。

## 2. 相同的交互要求

- “删去上下中段”：选择两条水平切线，删除 `[a,b)` 行，连接剩余部分。
- “删去左右中段”：选择两条垂直切线，删除 `[a,b)` 列，连接剩余部分；两方向第一版均支持。
- 切线顺序可反向，至少删除 1 像素，至少留下 1 像素；半开区间避免多删/漏删一行。
- 首次默认水平切线；拖动时画待删遮罩与尺寸提示，确认后显示拼合结果。
- 提供确认本次、取消本次、撤销/重做、退出工具；未确认切线不能影响复制/保存。
- 复用滚轮缩放、Shift/Alt 平移、左键观察拖动、放大镜/Alt 精调；切线模式下左键用于选线，观察模式可明确切换。
- 裁剪边界、切线、OCR 框选、观察模式互斥，切换/捕获丢失需清理状态，不能留下放大镜。
- 默认不做动画、不持续后台处理；复制/保存/标注/OCR 接收确认后的图像。

## 3. 方案 A：每次确认立即生成新位图，保存有限快照

像素驱动：确认切除后用 CPU/DIB 或少量 BitBlt 把上下/左右两块复制到新位图。
编辑器直接把新位图作为下一次输入；撤销保留旧位图，按字节上限淘汰快照。

优势：与当前单 HBITMAP 绘制/导出模型最接近，结果坐标简单，无需分段绘制。
代价：每次确认都完整读写保留像素；撤销至少额外持有一个大图，连续切除峰值较高。
仅遮罩拖动不复制，但不能把“确认后完整复制”称为零开销。

设原图占用 `B = stride × height`，结果占用 `B'`，忽略屏幕缓冲时，
一次提交最少约 `B+B'`，含历史可到 `B+B'+historyBytes`。
普通小图可能是最低总成本：一次直接复制比复杂元数据调度更便宜；长图多次操作不优。

## 4. 方案 B：原图不变，保留区段映射，最后按需生成像素（推荐）

编辑模型驱动：持有一张不可变原图，维护保留的 X/Y 区间以及裁剪范围；
确认切除只更新映射，撤销记录元数据，不保存完整结果快照。
屏幕预览仅绘制与视口相交的片段；复制/保存/标注/OCR 时再生成必要结果或 ROI。

与 A 的核心差异：**编辑过程不反复重建全尺寸图像，结果主要是一个坐标映射。**
这不是用 GPU 或 worker 把同一份完整复制挪到别处。

实现约束：

1. 源图坐标、当前输出坐标、视口坐标分开。后续选线在当前输出坐标中，映射回源图区间后删除。
2. 上下与左右交替操作时，保留 X/Y 区间的笛卡尔积组成源图矩形块，不用全像素索引表。
3. 裁剪作为映射操作进入同一个有序历史，不能先保留原裁剪数值再随意缩小宽高。
4. 合并相邻源区间；建议初始最多 128 个绘制块、256 条历史命令，均为待测策略值。
   超限明确提示或由用户确认建立新基线，不能静默清空撤销/无限扩张。
5. 鼠标拖动只改候选线/遮罩；确认才改保留映射。只有视口大小变化时重建预览后备缓冲。
6. 缩放后的片段边界采用统一整数边界取整，防止 StretchBlt 在拼缝留缝/重叠；100% 导出必须逐像素准确。
7. 导出先用 64 位校验尺寸、stride 和乘法，再分配单张结果；检查失败完整回滚，原图/历史不能损坏。
8. 同一结果的 OCR/复制/保存尽可能复用单次物化结果，但不能让缓存常驻；操作结束释放临时图。

预估：编辑阶段约 `B + O(blocks+history)`，导出阶段约 `B+B'`，不含客户区预览缓冲和平台内部副本。
例如 2000×20000 BGRA 原图像素约 152.6 MiB；删除 20% 后结果约 122.1 MiB，
导出像素最低约 274.7 MiB。**B 避免反复快照，但并非大图内存变成几 MB。**

注意：左右切除每行要处理多个片段；大量交叉切除增加绘制调用。只画可见块、控制片段数量，
不能为了省复制却在平移时反复遍历和缩放整张长图。

## 5. 方案 C：GPU 纹理拼接与显示，最终读回

渲染驱动：将图上传纹理，编辑保留 GPU UV/矩形块，或通过 GPU 拷贝生成目标纹理；
用 D3D 绘制拼合预览，复制/PNG/OCR 时再回读到系统位图。
可做平滑交互，但全尺寸原纹理、结果纹理、staging 与 CPU 输入/输出可能同时存在。
超长图可能超过单纹理限制，必须分块；GPU 显存不足、设备丢失、远程桌面均需回退。

代价：静态图也引入上传和读回同步；若保留 GPU 全结果作撤销，内存仍膨胀。
即便只存 GPU 区段元数据，也不能免除原图纹理驻留和最终读回。
适合未来已统一 GPU 图像编辑器的场景，不适合目前 GDI Core 为一个删除操作新增渲染框架。

## 6. 资源比较与选择

| 方案 | 编辑中的额外内存 | 多次确认成本 | 空闲开销 | 适合当前架构 |
| --- | --- | --- | --- | --- |
| A 立即像素重建 | 至少一份结果；历史按图大小增长 | 每次复制结果图 | 无周期任务 | 最容易，但长图峰值大 |
| B 区段映射 | 小量区间/命令 + 视口缓冲 | 主要改元数据 | 无周期任务 | 推荐，需严格坐标测试 |
| C GPU 编辑 | 纹理/可能的 staging；可能与 CPU 图重复 | GPU 操作，导出有读回 | 驻留 GPU 资源 | 当前不选 |

**资源优先推荐 B**：长图多次操作通常更省 RAM/带宽，普通小图也能共用其逻辑。
这属于算法与现有架构推断，不是实测排序；不能保证所有小图都比 A 快。
先实现 B 的纯逻辑与 CPU 输出，暂不实现 C 或复杂多轨编辑。

## 7. 与现有功能的边界

- 首版先做结构编辑，再进入现有标注编辑；返回重新结构编辑时先确认如何处理已经烘焙的标注。
  跨切线的矢量形状第一版不做“智能语义挪动”，可由用户确认先烘焙再删除像素。
- OCR 的文字/框是旧图结果：编辑后必须重新识别或显式标记失效，不复用旧高亮坐标。
- 拼合图不再与一块连续屏幕区域一一对应；内部保留合成图来源，不能伪造原窗口坐标交给插件。
  API 2 使用既有图像任务契约及无可滚动来源的上下文，不占用 reserved 字段；新 provenance 另走版本化设计。
- 监控窗口提供“编辑当前帧”时先取得一张独立静态副本，切除结果不替换实时采集纹理/源 crop。
- 固定图也提供结构编辑入口，不能让普通图只有安装 Scroll 后才能进入。

## 8. 验证门禁

纯逻辑：两轴、交替、多段、相邻/重复区间、反向、边界、单像素、全删拒绝、裁剪组合、撤销重做。
像素测试：生成每行/列不同颜色的图，比对输出全部像素和拼缝，不能只比尺寸。
交互：100%/缩放/DPI 下选线映射、取消、捕获丢失、放大镜结束、复制/保存/区域 OCR。
资源：大图连续 20 次确认并撤销；检查没有 20 张完整历史图，没有后台循环；关闭后句柄/缓冲回收。
不装任何插件的 Core 测试必须通过，现有 OCR/Scroll workflow 必须保持可用。
